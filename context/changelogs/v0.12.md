# v0.12 变更记录

## 基本信息

- **完成时间**：2026-07-30
- **对应 PRD**：无独立 PRD；来源于开发环境与工程流程分阶段改造 Phase 4
- **版本定位**：不可变镜像晋级与安全发布门禁

## 实现内容

### immutable-images

- `main` 的 `CI / CI Required` 通过后，Backend 与 Frontend 各构建一次，以完整 commit
  SHA 标识并推送 GHCR；Staging 直接消费构建输出的 digest。
- 构建作业保存 90 天不可变 digest 清单；Production 从同一成功运行下载并校验清单，
  不在发布时重新解析可能被移动的 SHA tag。
- 新增 `compose.release.yml`，移除前后端运行时构建定义，只接受 `sha256` digest。
- Frontend 改为同源 API 请求，Nginx 将 `/api`、`/docs` 与 `/redoc` 转发至 Backend，
  环境间不再因 API 地址不同而重建前端镜像。

### release-gates

- Staging 自动部署由统一 CI 工作流在镜像构建后触发；原独立 staging 工作流改为只
  允许手动重部署已经存在完整成功运行的 `main` SHA。
- Production Release 验证 tag 提交属于 `main`，并要求同一提交存在成功的完整
  CI、镜像构建和 staging 运行；通过后才进入 `production` Environment 批准。
- Production 使用该次成功 CI/staging 运行记录的 digest，不在目标 Runner 重新构建。

### backup-migration-health-rollback

- 新增 `scripts/deploy-release.sh`，发布前验证必填变量、内网 HTTP 地址、稳定项目名和
  digest 镜像，且使用锁避免同一栈并发部署。
- 发布顺序固定为数据库健康、宿主机 PostgreSQL 备份、迁移/初始化、应用切换和前后端
  健康检查；同时通过 Frontend 地址检查同源 API 转发，备份必须非空后才进入迁移。
- 迁移失败时停止且不切换应用。新应用健康失败时恢复已记录的上一组镜像，不自动执行
  schema downgrade；回退也失败时明确要求人工恢复。

## verification

- 开发、内网、release Compose 渲染通过；release 配置确认无 `build`。
- 发布脚本 Shell 语法与行为回归通过：成功发布、拒绝可变 tag、迁移失败停止、健康
  失败镜像回退、部署状态保持和非空备份均已覆盖。
- 完整后端、前端、E2E 与工作流静态验证结果随本阶段最终验证记录。

## 外部完成边界

代码和配置清单已交付，但本地任务没有权限配置 GHCR、GitHub Environments、
Environment Secrets、self-hosted Runner 或 NAS，也未获准 push、发布 Release 或部署。
因此实际 staging 健康/冒烟证据尚不存在，H 级发布变更在这些外部配置完成并运行前
保持未完成，不能把本地测试描述为 staging 通过。
